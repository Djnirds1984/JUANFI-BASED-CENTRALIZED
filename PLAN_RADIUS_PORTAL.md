# RADIUS Captive Portal with Toggle - Final Implementation Plan

## Overview
Add dual-mode captive portal support:
- **Local mode** (current): MikroTik hosts portal files, RADIUS validates
- **RADIUS mode** (new): Panel hosts portal files, panel's RADIUS server handles ALL auth (no proxying to MikroTik)

Admin can toggle per-router which mode to use. Each router has independent settings.

---

## Architecture

### Local Mode (Current - No Changes)
```
User → MikroTik hotspot → serves login.html from MikroTik
     → user submits → MikroTik validates via RADIUS → Access-Accept → online
```
- Portal files: served from MikroTik's `/hotspot/` folder
- Auth: MikroTik → RADIUS (panel)
- Status page: MikroTik's status.html

### RADIUS Mode (New - Pure RADIUS)
```
User → MikroTik hotspot → RADIUS intercept → redirect to panel
     → panel serves login.html → user submits → panel's RADIUS validates → Access-Accept
     → panel redirects to status.html → session tracking via RADIUS accounting
```
- Portal files: served from panel at `http://10.0.0.252:3000/portal/{router-id}/`
- Auth: Panel's RADIUS server (no MikroTik proxy)
- Status page: Panel's status.html with RADIUS session data
- MikroTik role: just redirect + walled garden

---

### 2. Portal File Serving (`src/api/portal.ts` - NEW FILE)
Express routes to serve portal files when router is in RADIUS mode:

```typescript
// Serve portal files with MikroTik variable injection
GET  /portal/:routerId/login.html
GET  /portal/:routerId/status.html
GET  /portal/:routerId/rlogin.html
GET  /portal/:routerId/algo.js
GET  /portal/:routerId/md5.js
GET  /portal/:routerId/assets/*      // CSS, JS, images, themes

// Auth endpoints (pure RADIUS, no MikroTik proxy)
POST /portal/:routerId/login         // Validate via RADIUS, create session
POST /portal/:routerId/logout        // Send RADIUS Accounting-Stop

// API endpoints for portal
GET  /portal/:routerId/api/status    // Get session info from RADIUS
```

**MikroTik variable injection:**
Replace MikroTik template variables with actual values from query params:
- `$(mac)` → from `?mac=XX:XX:XX:XX:XX:XX`
- `$(ip)` → from `?ip=X.X.X.X`
- `$(server-address)` → from router config (router.host)
- `$(interface-name)` → from router config
- `$(chap-id)` → generated by panel (random 1-byte hex)
- `$(chap-challenge)` → generated by panel (random 16-byte hex)
- `$(link-login-only)` → `/portal/{routerId}/login`
- `$(link-status)` → `/portal/{routerId}/status.html`
- `$(link-redirect)` → from query param or router config

**Theme support:**
- Read theme from `?theme=xxx` query param or router config
- Serve appropriate CSS/assets from `hotspot/assets/` subdirectories
- All 4 themes work identically to local mode

### 3. RADIUS Auth Handler (`src/services/portalAuth.ts` - NEW FILE)
Pure RADIUS authentication (no MikroTik proxy):

```typescript
// Generate CHAP challenge
function generateChapChallenge(): { chapId: string, chapChallenge: string }

// Validate credentials via RADIUS
async function authenticateViaRadius(
  routerId: number,
  username: string,
  chapId: string,
  chapResponse: string,
  chapChallenge: string,
  userIp: string,
  macAddress: string
): Promise<{ success: boolean, sessionTimeout?: number, profile?: string }>

// Send RADIUS Accounting-Start
async function sendAccountingStart(
  routerId: number,
  username: string,
  sessionId: string,
  userIp: string,
  macAddress: string
): Promise<void>

// Send RADIUS Accounting-Stop
async function sendAccountingStop(
  routerId: number,
  username: string,
  sessionId: string,
  userIp: string,
  macAddress: string,
  sessionTime: number,
  inputOctets: number,
  outputOctets: number
): Promise<void>
```

**Flow:**
1. User loads `/portal/{routerId}/login.html?mac=X&ip=Y`
2. Panel generates CHAP challenge, injects into HTML
3. User submits form with username + CHAP response
4. Panel validates via RADIUS Access-Request
5. On success: RADIUS returns session timeout, profile
6. Panel sends RADIUS Accounting-Start
7. Panel redirects to `/portal/{routerId}/status.html`
8. Status page reads session from RADIUS sessions table

## Frontend Portal Changes

### login.html Modifications
The portal's `login.html` needs to work in both modes:

**Local mode (unchanged):**
- MikroTik injects variables server-side
- Form submits to `$(link-login-only)` (MikroTik's `/login`)

**RADIUS mode (new):**

- Form submits to `/portal/{routerId}/login` (panel endpoint)
- Panel validates via RADIUS, redirects to status page

**No changes needed to login.html template** - it already uses `$(link-login-only)` which will be injected differently based on mode.

### status.html Modifications
Similar to login.html - works in both modes:

**Local mode:**
- MikroTik serves status.html with session variables
- Logout button submits to `$(link-logout)`

**RADIUS mode:**
- Panel serves status.html, fetches session from RADIUS DB
- Logout button POSTs to `/portal/{routerId}/logout`
- Panel sends RADIUS Accounting-Stop

## MikroTik Configuration

### For RADIUS Mode Routers

**Option A: RADIUS Intercept URL (Recommended)**
```routeros
# 1. Add panel IP to walled garden
/ip hotspot walled-garden add action=accept dst-host=10.0.0.252 http-host=10.0.0.252

# 2. Configure hotspot profile to redirect via RADIUS
/ip hotspot profile set [find name="default"] \
  login-by=http-pap \
  radius-intercept=yes \
  radius-intercept-url="http://10.0.0.252:3000/portal/{router-id}/login.html?mac=\$(mac)&ip=\$(ip)"

# 3. Ensure RADIUS client is configured
/radius add address=10.0.0.252 secret=YOUR_SECRET authenticate=yes account=yes
```

**Option B: Static Redirect (Fallback)**
```routeros
# If radius-intercept-url not supported, use on-login script
/ip hotspot user profile set [find name="default"] \
  on-login=":delay 1; /tool fetch url=\"http://10.0.0.252:3000/portal/{router-id}/redirect?mac=\$(mac)&ip=\$(ip)\" keep-result=no"
```

## Risks & Mitigations

### Risk 1: MikroTik RADIUS intercept not supported
**Problem:** Some MikroTik versions don't support `radius-intercept-url`
**Mitigation:** Provide fallback Option B (on-login script redirect)

### Risk 2: CHAP challenge mismatch
**Problem:** Panel generates CHAP challenge, but RADIUS expects specific format
**Mitigation:** Use existing RADIUS server code (already handles CHAP correctly)

### Risk 3: Session tracking divergence
**Problem:** MikroTik sessions vs RADIUS sessions
**Mitigation:** In RADIUS mode, use RADIUS sessions table as source of truth. Don't sync to MikroTik.

### Risk 4: Panel downtime = RADIUS portals down
**Problem:** If panel is down, RADIUS mode portals don't work
**Mitigation:** 
- Admin can toggle back to local mode immediately
- Panel has uptime monitoring
- Document this limitation

### Risk 5: Walled garden misconfiguration
**Problem:** Admin forgets to add panel IP to walled garden
**Mitigation:** 
- Show clear error message if walled garden not configured
- Provide copy-paste MikroTik config in admin UI
- Add "Test Connection" button
